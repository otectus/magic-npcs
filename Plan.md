# Technical Critique: NPC Spellcasting Mod (Iron's Spells 'n Spellbooks × NPC mods, Forge 1.20.1)

## TL;DR
- **Stop reinventing the resource layer.** Iron's already ships `MagicData` (a capability), Forge attributes (`MAX_MANA`, `MANA_REGEN`, `SPELL_POWER`, `CAST_TIME_REDUCTION`, `COOLDOWN_REDUCTION`), a `PlayerCooldowns` object, and an `AbstractSpellCastingMob` / `IMagicEntity` mob-casting framework — the plan's custom `int mana` field, custom cooldown map, and from-scratch cast goal are the wrong approach and should be deleted.
- **Several API names in the plan are factually wrong.** The real casting entry is `AbstractSpell.onCast(Level, int spellLevel, LivingEntity, CastSource, MagicData)` (not a `canBeCastBy(LivingEntity)` → `CastResult` flow, which does not exist); spells register via a `DeferredRegister<AbstractSpell>` against `SpellRegistry.SPELL_REGISTRY_KEY`; and the Recruits base class is `AbstractRecruitEntity`, not `EntityVillagerRecruits`/`VillagerRecruitsEntity`.
- **The 1.20.1 code sketches use removed pre-1.19 APIs.** `CapabilityManager.INSTANCE.register(...)` + `Storage` must become `RegisterCapabilitiesEvent` + `CapabilityToken`; `SimpleChannel`/`NetworkEvent.Context` is still correct for 1.20.1; and the manual client particle packet double-plays effects Iron's already spawns server-side.

## Key Findings

**Iron's exposes a real, stable addon API.** The package `io.redspace.ironsspellbooks.api.**` is published as a separate `apiJar` and is explicitly the "stable" surface for addon developers; packages outside `api` give you "all the same tools that we do, but you might encounter breaking changes in future releases" (iron.wiki/developers). On Forge 1.20.1, depend on it with `compileOnly fg.deobf("io.redspace:irons_spellbooks:${ver}:api")` + `runtimeOnly fg.deobf("io.redspace:irons_spellbooks:${ver}")` (the official Forge dependency snippet from iron.wiki/developers).

**The mob-casting layer already exists.** `AbstractSpellCastingMob` (package `io.redspace.ironsspellbooks.entity.mobs.abstract_spell_casting_mob`) extends vanilla `PathfinderMob` and implements `IMagicEntity`. It is the base for the mod's own Pyromancer, Cryomancer, Priest, Apothecarist, Necromancer, and Archevoker NPCs and bosses (Dead King `DeadKingBoss`, Keeper `KeeperEntity`, Fire Boss). It provides mana/cast state, GeckoLib animation handling, and goal-based AI, and mobs cast from `CastSource.MOB`.

**`MagicData` attaches to living entities, not just players.** Spell-casting mobs use the same `MagicData` + `SyncedSpellData` architecture as players. DeepWiki's indexed source (AbstractSpellCastingMob.java:45-108) states verbatim: "Non-player entities like mobs can also cast spells using similar mechanics to players."

**Licensing is restrictive on both sides.** Iron's uses a custom license that permits "Fork and modify the code as long as modifications are not distributed publicly" and forbids you to "Use or redistribute ANY assets of this mod, even for personal use" (verbatim from the LICENSE in iron431/irons-spells-n-spellbooks; it otherwise carries the MIT-style "THE SOFTWARE IS PROVIDED 'AS IS', WITHOUT WARRANTY OF ANY KIND" disclaimer). Recruits' GitHub repo states "All Rights Reserved unless otherwise explicitly stated" and CurseForge lists it as All Rights Reserved. Neither permits redistribution — depending on Iron's `:api` only (and soft-depending on Recruits) is the safe path.

## Details

### A. Correctness fixes (the plan's API assumptions are wrong)

**A1. Spell class hierarchy & casting entry point.**
- Real base class: `AbstractSpell` in `io.redspace.ironsspellbooks.api.spells`. Confirmed.
- The plan's claimed `canBeCastBy(LivingEntity)` returning a `CastResult` is **not** the real entry point. The real cast method is `onCast(Level level, int spellLevel, LivingEntity entity, CastSource castSource, MagicData playerMagicData)`. This is confirmed in the official Iron's changelog (iron.wiki/changelog), which records: "AbstractSpell#onCast(Level, int, LivingEntity, MagicData) (Previously replace by onCast(Level, int, LivingEntity, CastSource, MagicData))" — i.e., the **five-argument CastSource form is the 1.20.1 / 3.x form** (the four-arg form is the later 1.21 change). The official porting guide on iron.wiki/developers also shows this five-arg signature in its summon-spell skeleton.
- The higher-level item/player flow goes through `AbstractSpell.attemptInitiateCast(...)`, called from `ServerPlayerEvents.onUseItem`, which reads the active spell from `SpellSelectionManager` (confirmed by DeepWiki: SpellSelectionManager.java:48-100; ServerPlayerEvents.java:126-181). Other real per-spell hooks include `getMana(int, LivingEntity)`, `getSpellPower(...)`, `getCastTime(int)`, `getRecastCount(int, LivingEntity)`, and `getDefaultConfig()`.
- Cast types are `INSTANT`, `CONTINUOUS`, `LONG` (enum `CastType`); cast sources are `SPELLBOOK`, `SCROLL`, `SWORD`, `MOB` (enum `CastSource`, package `io.redspace.ironsspellbooks.api.spells`).

**A2. Mob casting — do NOT reinvent it.** To make a mob cast, the idiomatic call on an `AbstractSpellCastingMob` / `IMagicEntity` is `initiateCastSpell(AbstractSpell, int spellLevel)`, with `cancelCast()` and `castComplete()` managing state. The mod's own AI goals — `WizardAttackGoal` (base spell combat), `WarlockAttackGoal` (melee + spells), `AlchemistAttackGoal` (potion-throwing), `WizardSupportGoal` (heal/buff allies), and `SpellBarrageGoal` (sequenced barrages) — drive spell selection and targeting (DeepWiki, AbstractSpellCastingMob.java:412-534). These goals are tightly coupled to `AbstractSpellCastingMob`/`IMagicEntity` (spell selection, animation state, the mob's `MagicData`) and are generally **not** directly attachable to an arbitrary vanilla `Mob` without that base type. (Exact constructor parameters could not be byte-for-byte confirmed from public docs — see Caveats.)

**A3. Mana / resource system.** Mana is driven by Forge **attributes** registered in `AttributeRegistry`. Confirmed in-game IDs include `irons_spellbooks:max_mana`, `irons_spellbooks:cooldown_reduction`, and `irons_spellbooks:cast_time_reduction` (visible in the repo's `NOTES.MD` `/attribute` examples), plus `MANA_REGEN`, `SPELL_POWER`, and per-school spell-power/resistance attributes (e.g., Eldritch power/resistance added later). The mana capability is `MagicData` (package `io.redspace.ironsspellbooks.api.magic`; formerly "PlayerMagicData"), with cooldowns stored in `PlayerCooldowns` (`io.redspace.ironsspellbooks.capabilities.magic.PlayerCooldowns`), recasts in `PlayerRecasts`/`RecastInstance`, and client-synced state in `SyncedSpellData`. Mana regen is computed from `MANA_REGEN` as a percentage of max mana inside `MagicManager`. **The plan's custom `int mana` and custom cooldown map are wrong** — scale via attribute modifiers and read/write `MagicData`/`PlayerCooldowns`.

**A4. Spell registry.** It is a **custom registry built on `DeferredRegister<AbstractSpell>`** against `SpellRegistry.SPELL_REGISTRY_KEY` (registry id `irons_spellbooks:spells`), **not** a static map and **not** the vanilla block/item registry. The official developer docs show the exact registration pattern: `DeferredRegister.create(SpellRegistry.SPELL_REGISTRY_KEY, MODID)` and `SPELLS.register(spell.getSpellName(), () -> spell)`. Lookup is `SpellRegistry.getSpell(...)` (resolves a spell by id; there is also a `none()` sentinel) and `getSpellsForSchool(...)`. Supporting types: `SchoolType` (registered via `SchoolRegistry`), `SpellRarity` (common/uncommon/rare/epic/legendary), and a spell tier/level concept. New schools are registered via `SchoolRegistry` and (on 1.20.1+) require an associated damage type.

**A5. Projectiles/effects with a non-player caster.** Iron's own mobs cast projectile spells from `CastSource.MOB`, so `LivingEntity` casters are first-class — the plan's worry is unfounded. The server-side spell logic already spawns the spell's particles and sounds during `onCast`, so replaying them via a separate client packet is redundant and will double-play.

**A6. Recruits entity classes.** The plan's guesses `EntityVillagerRecruits`/`VillagerRecruitsEntity` are wrong. The real base class is `AbstractRecruitEntity` (`com.talhanation.recruits.entities`), confirmed by DeepWiki's indexed Recruits source (AbstractRecruitEntity.java:81-145): "AbstractRecruitEntity provides core functionality including ownership (OWNER_ID), group membership (GROUP), AI state management (STATE, FOLLOW_STATE), and combat mechanics." It is a custom combat pathfinder mob (specialized subclasses add ranged/mounted combat), **not** an `AbstractVillager`/`Villager` subclass; entity types are registered in `ModEntityTypes`. Synchronized `EntityDataAccessor` fields include `OWNER_ID`, `GROUP`, `STATE` (0 neutral / 1 aggressive / 2 raid / 3 passive), `FOLLOW_STATE`, plus `HUNGER`, `MORAL`, and progression fields `LEVEL`, `XP`, `KILLS` — the `LEVEL` field is the natural driver for mana scaling.

### B. Architectural improvements

**B1. Lean on Iron's existing systems.** Delete the custom mana/cooldown/cast-goal code. For NPCs whose class you control, extend `AbstractSpellCastingMob`. For NPCs from *other* mods (the general case), do **not** subclass — attach `MagicData` and the mana attributes to the `LivingEntity`, then inject a casting goal that calls `onCast(level, spellLevel, npc, CastSource.MOB, magicData)`.

**B2. Mod-agnostic adapter/registry design (matches the user's goal).**
- **Core capability:** a `SpellcastingHandler` capability (your own) attached via `AttachCapabilitiesEvent<Entity>`, holding the entity's chosen spell list, current target, and a tick scheduler. Mana itself should ride Iron's `MagicData` + attributes rather than duplicating into your capability.
- **Attribute-based mana pool:** add Iron's mana attributes (or your own scaling modifiers layered on top) to opted-in entity types via `EntityAttributeModificationEvent`, so arbitrary mobs gain `max_mana` etc.
- **Tag-driven opt-in:** an `EntityTypeTags`-style data tag (e.g., `yourmod:spellcasters`) listing which entity types receive the casting goal; check membership in `EntityJoinLevelEvent` and inject at runtime with `mob.goalSelector.addGoal(...)`. This is datapack-overridable and needs no hard dependency.
- **Per-mod adapter modules:** small optional classes guarded by `ModList.get().isLoaded("recruits")` etc., each translating mod-specific concepts (Recruits ownership/teams/`LEVEL`) into your core's target-selection and mana-scaling inputs. This mirrors how mature compat mods are structured — e.g., **Ars 'n Spells** (otectus/ars-n-spells) bridges Ars Nouveau and Iron's on 1.20.1 Forge with Iron's made "actually optional now," its handler "instance-registered behind the existing `ModList.get().isLoaded("irons_spellbooks")` block," and its Iron's attribute references "converted to lazy double-checked init."

**B3. Recruits integration specifics.** Recruits exposes no public Java API/events for this purpose; integrate via `EntityJoinLevelEvent` (goal injection) + `AttachCapabilitiesEvent` (your handler). Its goal selector is the standard vanilla `GoalSelector`, so runtime `addGoal` is feasible. Reuse its team/ownership system (`OWNER_ID`, `GROUP`, the `RecruitsDiplomacyManager` ALLY/ENEMY/NEUTRAL relations) for friendly-fire-safe targeting, and its `LEVEL`/rank for mana scaling. Recruits ships Mixin (MixinGradle in its build), so Mixin injection is technically available, but event-based goal injection is lower-risk and should be preferred; reserve Mixin for cases where you must reorder existing goal priorities.

### C. Forge 1.20.1 code corrections

**C1. Capabilities.** The sketch's `CapabilityManager.INSTANCE.register(class, storage, factory)` + `Storage` class is pre-1.19 and was removed in 1.19+. The correct 1.20.1 pattern:
- Declare the token: `public static final Capability<SpellcastingHandler> HANDLER = CapabilityManager.get(new CapabilityToken<>(){});`
- Register in `RegisterCapabilitiesEvent`: `event.register(SpellcastingHandler.class);`
- Attach via `AttachCapabilitiesEvent<Entity>` using an `ICapabilitySerializable<CompoundTag>` provider. There is no `IStorage`/`Storage` anymore — NBT serialization lives directly in the provider. (This is also how Iron's itself attaches `MagicData`: its changelog references fixing "default magic data attachment," and the mod hooks `AttachCapabilitiesEvent`.)

**C2. Networking.** `SimpleChannel` + `NetworkEvent.Context` is **still correct** on Forge 1.20.1 (the custom-payload API arrived later, ~1.20.4/NeoForge). Use `NetworkRegistry.newSimpleChannel(...)` with a protocol-version string and accept predicates, register messages with incrementing integer IDs via `INSTANCE.registerMessage(id, type, encoder, decoder, handler)`, and in the handler call `ctx.get().enqueueWork(...)` then `ctx.get().setPacketHandled(true)`. (Recruits itself uses a `SIMPLE_CHANNEL` for all client-server traffic on 1.20.1, confirming this idiom is current.)

**C3. Particles/sounds.** The sketch's `npc.level.addParticle(...)` plus `SpellRegistry.getSpell(spellId).getParticleType()`/`.getSoundEvent()` is unsafe on two counts: spells do not generally expose those accessors, and `addParticle` is client-only (it no-ops server-side). Because Iron's already emits the spell's particles and sounds server-side during `onCast`, a manual client packet is redundant and will double-play effects. Remove it and rely on Iron's effect spawning.

**C4. Ticking & sync.** Per-entity mana regen and cast ticking should hook `LivingTickEvent` (or the injected goal's `tick()`), **server-side only**. For client sync, prefer Iron's existing `SyncedSpellData` (entity-data-style syncing) over a hand-rolled packet; if you add `SpellcastingHandler` state the client needs, sync it on `PlayerEvent.StartTracking` (tracking start) and on change — mirroring how Iron's keeps `MagicData` in sync via `SyncEntityDataPacket`/`SyncAnimationPacket` for its mobs.

**C5. GeckoLib animations on a villager-based model.** Recruits' recruits are not GeckoLib models, so full custom cast animations are unrealistic without replacing the renderer/model. Realistic 1.20.1 scope: trigger vanilla arm-swing (`mob.swing(hand)`) and let the spell's own projectile/particle feedback sell the cast; reserve true GeckoLib cast animations for entities that are already GeckoLib (Iron's `AbstractSpellCastingMob` descendants). Real-world caution: overriding GeckoLib's `GeoModel.handleAnimations` (a `final` method) has caused `IncompatibleClassChangeError` startup crashes when GeckoLib/Iron's versions mismatch (Iron's issue #1016) — do not subclass/override Iron's model classes.

### D. Dependencies, balance, performance, licensing, risk

**D1. Dependencies (1.20.1, Iron's 3.x).** Iron's 1.20.1 requires **GeckoLib, Curios API, Caelus API, and PlayerAnimator**, all required on client and server (confirmed on Modrinth/CurseForge dependency listings). Exact compatible versions for the 3.4.x line are documented in Iron's GitHub issue #678 for **v1.20.1-3.4.0.4** (Forge 47.3.12): **Caelus API Forge-3.20+1.20.1, Curios API Forge-5.11.0+1.20.1, PlayerAnimator Forge-1.0.2-rc1+1.20, and GeckoLib Forge-1.20.1-4.4.9.** The latest 3.4.x backport build is `v1.20.1-3.4.0.9` (May 2, 2025); a newer `1.20.1-3.15.6` (Apr 10, 2026) also exists. Always confirm the exact pins from the specific jar's `META-INF/mods.toml` you target.

**D2. Balance / performance.** Scale mana and spell power off the NPC's level/rank (Recruits `LEVEL`) via attribute modifiers rather than hard-coded values; cap cast frequency through the spell's own cooldown via `PlayerCooldowns` instead of a custom timer. Performance: gate goal injection behind the entity tag so only opted-in mobs pay AI cost, and cache the capability `LazyOptional` instead of resolving it every tick.

**D3. Licensing / risk.** Build only against Iron's `:api` artifact and do **not** bundle or redistribute Iron's or Recruits jars or assets (Iron's license forbids public distribution of modified code and any asset redistribution; Recruits is All Rights Reserved). Soft-depend on both so your mod loads without them present. The primary technical risk is that anything outside Iron's `api` package may break between 3.x releases — keep adapter code thin and isolated so a single file absorbs any breakage.

## Recommendations
1. **Immediately:** remove the custom `int mana`, the custom cooldown map, and the bespoke cast goal. Replace with Iron's attributes (`max_mana`/`mana_regen`/`spell_power`/`cooldown_reduction`/`cast_time_reduction`) + `MagicData` + `PlayerCooldowns`. **Benchmark to clear this stage:** a recruit casts Iron's Magic Missile from `CastSource.MOB`, consumes mana visible via `/attribute … irons_spellbooks:max_mana`, and respects the spell cooldown.
2. **Next:** build the mod-agnostic core — `SpellcastingHandler` capability (1.20.1 `RegisterCapabilitiesEvent` + `CapabilityToken` pattern), a `yourmod:spellcasters` entity tag, and `EntityJoinLevelEvent` goal injection. **Threshold to proceed:** a plain tagged vanilla mob casts correctly with Recruits absent.
3. **Then:** add the Recruits adapter (ownership/diplomacy-aware targeting, `LEVEL`-scaled mana) behind `ModList.get().isLoaded("recruits")`. Add further per-mod adapters only as concrete demand appears.
4. **Before release:** read exact dependency versions from the target Iron's jar's `mods.toml`, verify no doubled particles/sounds, and confirm you ship no third-party jars or assets.
5. **Change triggers:** if you must reorder existing goal priorities or touch non-`api` internals, escalate to a narrowly-scoped Mixin and pin the Iron's version; if Iron's `api` signatures shift in a future 3.x, update only the thin adapter.

## Caveats
- DeepWiki's indexed source reflects the **1.21.1 / NeoForge** branch. The 1.20.1 Forge branch uses Forge **capabilities** (not NeoForge attachments) and the **five-arg** `onCast(... CastSource ...)`. Class and method *names* are stable across branches, but a few exact 1.20.1 signatures — `MagicData.getMana()/setMana()/addMana()`, the precise `MagicManager` accessor that fetches `MagicData` for a `LivingEntity`, the full declared method list of `IMagicEntity`, and the `WizardAttackGoal`/`SpellBarrageGoal` constructor parameters — could not be byte-for-byte confirmed from public documentation. Verify these by decompiling `irons_spellbooks-1.20.1-3.4.0.9.jar` (focus on `api/magic/MagicData`, `capabilities/magic/MagicManager`, `entity/mobs/abstract_spell_casting_mob/IMagicEntity` and `AbstractSpellCastingMob`, the `entity/mobs/goals/` package, and `api/registry/SpellRegistry`) or by browsing the GitHub `1.20.1` branch directly.
- The dependency versions in D1 are confirmed for **v1.20.1-3.4.0.4** specifically; the exact pins can shift across 3.4.x patch builds, so reconfirm against the precise jar you ship with.

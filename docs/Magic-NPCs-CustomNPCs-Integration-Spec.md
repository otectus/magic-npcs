# Magic NPCs × CustomNPCs — Integration & Compatibility Spec

## 1. Summary

This specification targets the Magic NPCs `0.8.0` update. Its Magic NPCs baseline is repository commit `498c0befdaaf175a5fd28a9719f2eb7afe49c1ba`; that tree still declares version `0.7.0`, so every path below describes a change against the immediate pre-`0.8.0` source rather than an already-released `0.8.0` tree. `gradle.properties`

The CustomNPCs baseline is the supplied `CustomNPCs-1.20.1-GBPort-Unofficial-1.20.1.20260711.jar`, whose manifest identifies `customnpcs-1.20.1-git` version `1.20.1.20260711`; its SHA-256 is `604916a1cd0949fd426cab5fad8f839037d7e6f74d9f18a9afbeaa7731edfc38`. `CustomNPCs-1.20.1-GBPort-Unofficial-1.20.1.20260711.jar!/META-INF/MANIFEST.MF`

The recommended design is an isolated, server-authoritative `compat/customnpcs/` module that adapts every real CustomNPCs NPC entity into Magic NPCs' existing composable NPC policy system. Magic NPCs already separates mod-specific ownership, diplomacy, rank, activity, targeting, and movement decisions behind `NpcAdapter`, and combines all applicable adapters conservatively; the CustomNPCs work should evolve that seam into a resolved `MagicNpc` contract rather than adding a second parallel integration framework. `src/main/java/com/otectus/magicnpcs/core/adapter/NpcAdapter.java`, `src/main/java/com/otectus/magicnpcs/core/adapter/NpcAdapters.java`

The critical interoperability defect is AI ownership. CustomNPCs periodically clears both its goal and target selectors and rebuilds them, which removes Magic NPCs' injected casting and movement goals. CustomNPCs then publishes `NpcEvent.UpdateEvent` on its own API event bus every ten ticks, after `super.tick()` and therefore after the same-tick `aiStep()` rebuild path in the inspected bytecode. The first implementation should subscribe to that API bus and repair only missing Magic NPCs-owned goals; it should not mix into CustomNPCs. `CustomNPCs JAR!/noppes/npcs/entity/EntityNPCInterface.class`, `CustomNPCs JAR!/noppes/npcs/EventHooks.class`, `CustomNPCs JAR!/noppes/npcs/api/event/NpcEvent$UpdateEvent.class`, `CustomNPCs JAR!/noppes/npcs/api/wrapper/WrapperNpcAPI.class`

That event-order conclusion is strong static evidence but remains a release-gating runtime assertion: **UNVERIFIED U-02 —** prove on both integrated and dedicated servers that a CustomNPCs AI edit removes and then restores exactly one Magic NPCs goal in the same tick, before the next selector evaluation. If it fails, the deferred fallback is a narrow optional `updateTasks` tail mixin with `require = 0`, version gating, and automatic compat disablement—not a mandatory baseline mixin. `CustomNPCs JAR!/noppes/npcs/entity/EntityNPCInterface.class`

The integration is opt-in by default. Installing CustomNPCs must not silently turn authored quest-givers, traders, builders, puppets, or dialogue actors into combat casters. A CustomNPC becomes eligible only through an explicit Magic NPCs loadout, manual School Tome/command assignment, or an independently enabled `[schools.customnpcs]` roll policy. Magic NPCs already gives manual school state precedence over automatic state and datapack loadouts, and already treats NPC framework adapters as policy inputs rather than universal eligibility. `src/main/java/com/otectus/magicnpcs/core/SchoolData.java`, `src/main/java/com/otectus/magicnpcs/integration/irons/CasterReconciler.java`, `src/main/java/com/otectus/magicnpcs/core/adapter/NpcAdapter.java`

No CustomNPCs source change is required or recommended. Direct references to `noppes.npcs.api.*` belong only in version-gated compat leaf classes. Common Magic NPCs startup, registries, commands, datapack parsing, generic adapters, and Iron's integration must remain free of CustomNPCs linkage so a missing or incompatible JAR produces one diagnostic and disables only this compat feature. `src/main/java/com/otectus/magicnpcs/MagicNpcs.java`, `src/main/java/com/otectus/magicnpcs/compat/EasyNpcCompat.java`, `src/main/java/com/otectus/magicnpcs/compat/easynpc/EasyNpcIntegration.java`

## 2. Environment & Assumptions

### 2.1 Binding platform contract

This plan treats the prompt's platform constraints as requirements, not discoveries:

- Minecraft `1.20.1`, Forge `47.x`, Java `17`, ForgeGradle `6`.
- Registrations use `DeferredRegister` plus `RegistryObject` over `ForgeRegistries.*`; configuration uses `ForgeConfigSpec`; networking uses `SimpleChannel`.
- Resource directories are plural, `pack_format` is `15`, and APIs from later Minecraft/Forge eras—including `DeferredHolder`, `ModConfigSpec`, the payload API, and `ResourceLocation.parse`—are prohibited.
- CustomNPCs is a soft dependency. Client types must not be loaded on a dedicated server.
- Every event hookup below identifies its bus explicitly.

The inspected Magic NPCs build matches this platform: ForgeGradle is `[6.0,6.2)`, the Java toolchain/release is `17`, Forge is `47.4.16`, Minecraft is `1.20.1`, and its pack metadata is `15`. `build.gradle`, `gradle.properties`, `src/main/resources/pack.mcmeta`

The supplied CustomNPCs descriptor accepts Forge `[47,)` and Minecraft `[1.20.1,1.21)`, declares mod ID `customnpcs`, and has no declared required third-party mod. `CustomNPCs JAR!/META-INF/mods.toml`

That descriptor declares license `CC BY-NC`. This plan does not interpret that license as permission to bundle or republish the binary; the JAR remains a locally supplied compile/test fixture unless the rights holder's terms are separately confirmed. `CustomNPCs JAR!/META-INF/mods.toml`

## 3. Mod Inventory — Magic NPCs

### 3.1 NPC representation and registration

Magic NPCs does not register an NPC entity type, NPC entity subclass, block, block entity, effect, sound event, menu, or custom capability. Its only registry object is `magicnpcs:school_tome`, registered with `DeferredRegister<Item>` and `RegistryObject<Item>` against `ForgeRegistries.ITEMS`. `src/main/java/com/otectus/magicnpcs/registry/MagicNpcsItems.java`

An NPC is therefore any existing `Mob` selected by a datapack loadout, a persisted school assignment, or an adapter-specific school policy. Framework-specific meaning is supplied by `NpcAdapter`, whose current policy surface covers applicability, priority, mana scaling, progression level, automatic school assignment, current activity gates, attack-target permission, ally detection, and movement freedom. `src/main/java/com/otectus/magicnpcs/core/adapter/NpcAdapter.java`, `src/main/java/com/otectus/magicnpcs/integration/irons/CasterReconciler.java`

`NpcAdapters.resolve(Mob)` composes every applicable adapter: activity vetoes use logical AND, any protective relationship wins, scaling/progression comes from the highest-priority provider, and movement takes the most restrictive policy. This composition is material to CustomNPCs because CustomNPC faction rules must coexist with Magic NPCs' generic team, owner, raid-ally, and sitting-pet protection rather than replace them. `src/main/java/com/otectus/magicnpcs/core/adapter/NpcAdapters.java`, `src/main/java/com/otectus/magicnpcs/compat/generic/OwnableTeamAdapter.java`, `src/main/java/com/otectus/magicnpcs/compat/generic/RaidAllyAdapter.java`, `src/main/java/com/otectus/magicnpcs/compat/generic/SittingPetAdapter.java`

### 3.3 Behavior systems

Magic NPCs' behavior is additive: `CasterReconciler` resolves manual school, explicit datapack, and automatic school authority; installs/removes only Magic NPCs-owned `NpcSpellAttackGoal` and `CasterMovementGoal`; optionally wraps native attack goals for reversible suppression; grants one-time loadout equipment; and installs a self-defense target goal when needed. `src/main/java/com/otectus/magicnpcs/integration/irons/CasterReconciler.java`, `src/main/java/com/otectus/magicnpcs/core/util/AttackGoals.java`, `src/main/java/com/otectus/magicnpcs/core/util/SuppressedGoal.java`

`NpcSpellAttackGoal` performs server-side attack or self-support spell selection, decision throttling, range/line-of-sight checks, windup, cooldown, mana, friendly-fire, and bystander protection. Its goal flags are empty unless the `LOOK` flag is explicitly enabled, reducing contention with an owning NPC framework. `src/main/java/com/otectus/magicnpcs/integration/irons/NpcSpellAttackGoal.java`, `src/main/java/com/otectus/magicnpcs/core/util/LineOfFire.java`, `src/main/java/com/otectus/magicnpcs/config/MagicNpcsConfig.java`

`CasterMovementGoal` repositions only when the feature is enabled and the resolved adapter policy permits it; its policy model supports `FREE`, `ANCHORED`, and `PINNED`. `src/main/java/com/otectus/magicnpcs/core/caster/CasterMovementGoal.java`, `src/main/java/com/otectus/magicnpcs/core/adapter/NpcAdapter.java`

`IronsSpellcasterHandler` owns reload listeners, datapack sync, bounded reconciliation, entity join/leave handling, server ticks, living ticks, and commands. Its normal living-tick mana path returns when the Magic NPCs casting goal is absent, which makes same-tick post-CustomNPC repair important. `src/main/java/com/otectus/magicnpcs/integration/irons/IronsSpellcasterHandler.java`

There is no Magic NPCs dialogue, quest, faction, trader, schedule, spawning, clone, or template engine. The mod consumes host-NPC behavior through adapters and supplies spellcasting, school assignment, gear, combat movement, feedback, and diagnostics. `src/main/java/com/otectus/magicnpcs/core/adapter/NpcAdapter.java`, `src/main/java/com/otectus/magicnpcs/core/loadout/SpellcasterLoadout.java`

## 4. Mod Inventory — CustomNPCs

### 4.1 NPC representation and entity hierarchy

The actual NPC base is `EntityNPCInterface extends PathfinderMob`, implementing Forge spawn-data and vanilla ranged-attack interfaces. `EntityNPCFlying` extends that base; the normal humanoid, 64×32, Alex, classic, golem, crystal, dragon, pony, and slime variants ultimately derive from `EntityNPCInterface`. `EntityChairMount` and `EntityProjectile` are support entities and are not NPCs. `CustomNPCs JAR!/noppes/npcs/entity/EntityNPCInterface.class`, `CustomNPCs JAR!/noppes/npcs/entity/EntityNPCFlying.class`, `CustomNPCs JAR!/noppes/npcs/CustomEntities.class`

`EntityDialogNpc` is an unregistered dummy using the `customnpc` type for dialog/command presentation; it overrides tick to do nothing and can be constructed without joining the world. The compat layer must reject any wrapper whose vanilla entity is not actually added to a server world, avoiding a direct reference to this internal class. `CustomNPCs JAR!/noppes/npcs/entity/EntityDialogNpc.class`, `CustomNPCs JAR!/noppes/npcs/command/CmdDialog.class`, `CustomNPCs JAR!/noppes/npcs/packets/client/PacketDialogDummy.class`

CustomNPCs registers nine NPC entity types—`customnpcs:npcpony`, `npccrystal`, `npcslime`, `npcdragon`, `npcgolem`, `customnpc`, `customnpc64x32`, `customnpcalex`, and `customnpcclassic`—plus `customnpcchairmount` and `customnpcprojectile`. Registration is performed from a `RegisterEvent` subscriber on the **mod bus**. `CustomNPCs JAR!/noppes/npcs/CustomEntities.class`

When internal config `FixUpdateFromPre_1_12` is true (default false), each of the nine NPC registrations also creates a one-argument `ResourceLocation("customnpcs." + name)` legacy entry, which resolves in the default `minecraft` namespace. The integration must identify wrappers through the API rather than assume only canonical `customnpcs:*` IDs; automatic/loadout content should still name canonical IDs. `CustomNPCs JAR!/noppes/npcs/CustomEntities.class`, `CustomNPCs JAR!/noppes/npcs/CustomNpcs.class`

Each NPC owns component objects for display/model, statistics, inventory, AI, advanced behavior, scripting, transformations, timers, combat, role, job, dialogs, and faction state; it also holds synced entity-data flags such as role/job/faction display data, walking, interacting, killed, and attacking. `CustomNPCs JAR!/noppes/npcs/entity/EntityNPCInterface.class`, `CustomNPCs JAR!/noppes/npcs/entity/data/DataDisplay.class`, `CustomNPCs JAR!/noppes/npcs/entity/data/DataStats.class`, `CustomNPCs JAR!/noppes/npcs/entity/data/DataInventory.class`, `CustomNPCs JAR!/noppes/npcs/entity/data/DataAI.class`, `CustomNPCs JAR!/noppes/npcs/entity/data/DataAdvanced.class`, `CustomNPCs JAR!/noppes/npcs/entity/data/DataScript.class`, `CustomNPCs JAR!/noppes/npcs/controllers/data/DataTransform.class`

An internal `DataAbilities` list also exists, but its inspected `save` and `readToNBT` methods are empty and `ICustomNpc` exposes no ability accessor. It is therefore not a viable bridge for Magic spells or affinities in this build. `CustomNPCs JAR!/noppes/npcs/entity/data/DataAbilities.class`, `CustomNPCs JAR!/noppes/npcs/api/entity/ICustomNpc.class`

On the server, the entity creates and retains an `NPCWrapper`; `NpcAPI.getIEntity(Entity)` returns that wrapper for a CustomNPC and a generic wrapper for other entities. Code should therefore test the returned value with `instanceof ICustomNpc` rather than name-match entity classes or registry IDs. `CustomNPCs JAR!/noppes/npcs/entity/EntityNPCInterface.class`, `CustomNPCs JAR!/noppes/npcs/api/wrapper/WrapperNpcAPI.class`, `CustomNPCs JAR!/noppes/npcs/api/NpcAPI.class`

### 4.2 Persistence, clones, and global controllers

`EntityNPCInterface.addAdditionalSaveData` writes its component data, role/job, timers, script state, transform, killed time, total ticks alive, mod revision, and linked-NPC name into the entity NBT; the corresponding read path restores those components and schedules AI/client refresh. Forge-owned persistent entity data, including Magic NPCs' `ForgeData.magicnpcs`, is handled by the superclass/Forge entity serialization rather than by those CustomNPCs component methods. `CustomNPCs JAR!/noppes/npcs/entity/EntityNPCInterface.class`

The public wrapper's temporary data is an in-memory map, while stored data uses entity persistent Forge data under `CNPCStoredData` and accepts only numeric/string values. This is separate from both CustomNPC component NBT and Magic NPCs' `magicnpcs` compound. `CustomNPCs JAR!/noppes/npcs/api/wrapper/EntityWrapper.class`, `CustomNPCs JAR!/noppes/npcs/api/entity/IEntity.class`

CustomNPCs creates a world-specific `customnpcs` directory, or redirects data to its configured external location when `EnableExternalSaving` is enabled. Its controllers persist global data including `factions.dat`, `bank.dat`, `recipes.dat`, `transport.dat`, `spawns.dat`, and `global.dat`, with `_new`/`_old` rollover files in several controllers. `CustomNPCs JAR!/noppes/npcs/CustomNpcs.class`, `CustomNPCs JAR!/noppes/npcs/controllers/FactionController.class`, `CustomNPCs JAR!/noppes/npcs/controllers/BankController.class`, `CustomNPCs JAR!/noppes/npcs/controllers/RecipeController.class`, `CustomNPCs JAR!/noppes/npcs/controllers/TransportController.class`, `CustomNPCs JAR!/noppes/npcs/controllers/SpawnController.class`, `CustomNPCs JAR!/noppes/npcs/controllers/GlobalDataController.class`

Those managers and dialog/quest/clone/linked controllers expose process-global static `Instance` singletons that CustomNPCs loads/resets from its Forge lifecycle handlers. They are implementation ownership, not a stable Magic NPC integration registry; the bridge uses public handler interfaces where available and otherwise does not call controller singletons. `CustomNPCs JAR!/noppes/npcs/CustomNpcs.class`, `CustomNPCs JAR!/noppes/npcs/controllers/FactionController.class`, `CustomNPCs JAR!/noppes/npcs/controllers/DialogController.class`, `CustomNPCs JAR!/noppes/npcs/controllers/QuestController.class`, `CustomNPCs JAR!/noppes/npcs/controllers/ServerCloneController.class`, `CustomNPCs JAR!/noppes/npcs/controllers/LinkedNpcController.class`

Dialogs and quests use controller-managed JSON files and contain migration paths for older serialized `.dat` data. Player-specific CustomNPCs state is stored beneath `playerdata/<uuid>.json`. `CustomNPCs JAR!/noppes/npcs/controllers/DialogController.class`, `CustomNPCs JAR!/noppes/npcs/controllers/QuestController.class`, `CustomNPCs JAR!/noppes/npcs/controllers/data/PlayerData.class`

Server clones live under `customnpcs/clones/<tab>/<name>.json` with migration support for `clonednpcs.dat`; cloning starts from entity NBT and removes a list of instance-only tags such as position, path, and UUID. **UNVERIFIED U-03 —** the inspected cleanup list does not remove `ForgeData`, so Magic NPCs state appears copyable, but verify by assigning a school, creating/spawning a clone, and inspecting the spawned entity after restart before making clone inheritance a supported promise. `CustomNPCs JAR!/noppes/npcs/controllers/ServerCloneController.class`

Linked NPC templates live under `linkednpcs/*.json`. Refreshing a linked NPC copies selected CustomNPCs display, statistics, advanced, inventory, AI, transform, and model data; it does not visibly rewrite the Forge persistent-data compound in the inspected method, so Magic NPCs state should remain instance-local. `CustomNPCs JAR!/noppes/npcs/controllers/LinkedNpcController.class`

Script files and script-controlled data are kept in CustomNPCs world/script directories, including language scripts, world data, player scripts, and Forge scripts. `CustomNPCs JAR!/noppes/npcs/controllers/ScriptController.class`, `CustomNPCs JAR!/noppes/npcs/entity/data/DataScript.class`, `CustomNPCs JAR!/noppes/npcs/controllers/data/ForgeScriptData.class`, `CustomNPCs JAR!/noppes/npcs/controllers/data/PlayerScriptData.class`

### 4.3 Behavior systems

The CustomNPC entity tick calls `super.tick()`, emits its script/API update every ten ticks, updates timers every tick, and performs its main server AI work in `aiStep()`. The latter updates scenes, regeneration, faction behavior, linked-template refresh, client synchronization, combat state, and AI rebuilds; several of those operations run on a twenty-tick cadence. `CustomNPCs JAR!/noppes/npcs/entity/EntityNPCInterface.class`, `CustomNPCs JAR!/noppes/npcs/EventHooks.class`

AI supports retaliation/fight, panic, avoid, or no-response behavior; stand, wander, or moving-path modes; ground, flying, or swimming navigation; return-home, wandering range, door/water/shelter/LOS/leap controls; and multiple tactical combat patterns. These are exposed partly through `INPCAi`, but their integer meanings come from implementation constants rather than typed API enums. `CustomNPCs JAR!/noppes/npcs/api/entity/data/INPCAi.class`, `CustomNPCs JAR!/noppes/npcs/entity/data/DataAI.class`, `CustomNPCs JAR!/noppes/npcs/entity/EntityNPCInterface.class`

Roles include trader, follower, bank, transporter, postman, companion, and dialog behavior; jobs include bard, healer, guard, item giver, follower, spawner, conversation, chunk loader, puppet, builder, and farmer behavior. Role/job IDs are integer values selected by `DataAdvanced`. `CustomNPCs JAR!/noppes/npcs/entity/data/DataAdvanced.class`, `CustomNPCs JAR!/noppes/npcs/roles/RoleInterface.class`, `CustomNPCs JAR!/noppes/npcs/roles/JobInterface.class`

CustomNPCs owns factions, dialogs, quests, trades/recipes, banks, transport locations, scenes, natural-spawn definitions, scripted behavior, and explicit clone/template tools. `CustomNPCs JAR!/noppes/npcs/controllers/FactionController.class`, `CustomNPCs JAR!/noppes/npcs/controllers/DialogController.class`, `CustomNPCs JAR!/noppes/npcs/controllers/QuestController.class`, `CustomNPCs JAR!/noppes/npcs/controllers/RecipeController.class`, `CustomNPCs JAR!/noppes/npcs/controllers/BankController.class`, `CustomNPCs JAR!/noppes/npcs/controllers/TransportController.class`, `CustomNPCs JAR!/noppes/npcs/entity/data/DataScenes.class`, `CustomNPCs JAR!/noppes/npcs/controllers/SpawnController.class`

Natural-spawn integration injects at the head of `NoiseBasedChunkGenerator.spawnOriginalMobs`; a server tick handler also scans visible chunks every 400 ticks for configured spawning, and chunk-loader jobs can keep NPC areas active. `CustomNPCs JAR!/noppes/npcs/mixin/NoiseChunkGeneratorMixin.class`, `CustomNPCs JAR!/noppes/npcs/ServerTickHandler.class`, `CustomNPCs JAR!/noppes/npcs/roles/JobChunkLoader.class`

The principal integration hazard is `EntityNPCInterface.updateTasks()`: it stops and clears every wrapped goal, clears available goals, locked flags, and disabled flags on both goal selectors, then reconstructs CustomNPCs target, navigation, response, movement, role, and job goals. It runs when `updateAI` is consumed on the twenty-tick path and again on killed-state changes. `CustomNPCs JAR!/noppes/npcs/entity/EntityNPCInterface.class`, `CustomNPCs JAR!/noppes/npcs/mixin/GoalSelectorMixin.class`

Each CustomNPC construction also uses `MixinRangedAttributeAccessor` to set the global `Attributes.MAX_HEALTH` ranged attribute's maximum to `Double.MAX_VALUE`; that is process-wide rather than entity-local. Magic NPCs does not mutate that vanilla bound, but test baselines should distinguish this CustomNPC side effect from mana/max-health integration behavior. `CustomNPCs JAR!/noppes/npcs/entity/EntityNPCInterface.class`, `CustomNPCs JAR!/noppes/npcs/mixin/MixinRangedAttributeAccessor.class`, `src/main/java/com/otectus/magicnpcs/integration/irons/IronsAttributeHandler.java`

CustomNPCs also exposes a global `FreezeNPCs` flag; its `aiStep()` returns immediately when set. **UNVERIFIED U-07 —** vanilla call ordering could still allow an already-installed Magic NPCs goal to receive selector ticks while CustomNPCs' `aiStep()` is frozen, so verify that “freeze” suspends both native and spell behavior; otherwise add an exact-version reflective activity veto. `CustomNPCs JAR!/noppes/npcs/CustomNpcs.class`, `CustomNPCs JAR!/noppes/npcs/entity/EntityNPCInterface.class`

## 6. Integration Architecture

### 6.1 Architectural decision

Magic NPCs remains the owner of magic state and casting policy; CustomNPCs remains the owner of NPC identity, authored AI, roles/jobs, faction/dialog/quest state, editor synchronization, clones, and scripts. The bridge translates policy and emits events. It never mirrors the entire CustomNPCs model into Magic NPCs and never edits CustomNPCs controller files.

The abstraction should be a resolved, entity-bound `MagicNpc` view produced by the existing adapter registry. This is an evolution of `NpcAdapter`, not a Java interface retrofitted onto third-party entities: Magic NPCs cannot make `EntityNPCInterface` implement its contract without a mixin, and a marker interface would not solve composition with generic owner/team/raid adapters. Existing `NpcAdapter` implementations are stateless policy providers selected/composed by `NpcAdapters.resolve(Mob)`. `src/main/java/com/otectus/magicnpcs/core/adapter/NpcAdapter.java`, `src/main/java/com/otectus/magicnpcs/core/adapter/NpcAdapters.java`

Signature-only sketch:

```java
public interface MagicNpc {
    Mob entity();
    ResourceLocation frameworkId();
    Optional<UUID> ownerId();
    OptionalInt progressionLevel();
    double manaScale();
    Set<ResourceLocation> traits();
    boolean canAttackCast();
    boolean canSupportCast();
    boolean canTarget(LivingEntity target);
    boolean isAlly(LivingEntity other);
    NpcAdapter.MovementPolicy movementPolicy();
    ItemStack heldItem(InteractionHand hand);
    void setHeldItem(InteractionHand hand, ItemStack stack);
    void publish(MagicNpcSignal signal);
}
```

Purpose of each addition:

- `frameworkId()` identifies diagnostics/content policy without importing the framework; CustomNPCs returns `customnpcs:npc`.
- `ownerId()` makes ownership explicit but optional. The CustomNPC API supplies a resolved live owner, so an offline/unresolved owner remains empty rather than using an internal UUID field. `CustomNPCs JAR!/noppes/npcs/api/entity/ICustomNpc.class`
- `progressionLevel()` is optional instead of conflating “no level system” with zero. CustomNPCs exposes no NPC progression level in `ICustomNpc`, so the adapter returns empty and the school roll uses no level gate. `CustomNPCs JAR!/noppes/npcs/api/entity/ICustomNpc.class`
- `traits()` exposes stable, data-driven predicates such as `customnpcs:role/trader`, `customnpcs:job/healer`, and `customnpcs:faction/3`; it avoids leaking CustomNPCs API types into loadout parsing.
- Separate attack/support activity gates preserve the current rule that a passive/working state may block aggression without necessarily blocking self-healing. `src/main/java/com/otectus/magicnpcs/core/adapter/NpcAdapter.java`
- Equipment accessors let a framework synchronize its authoritative inventory while the generic view continues to use vanilla hand slots.
- `publish()` is a neutral signal path. The CustomNPC implementation can call `ICustomNpc.trigger`; generic NPCs use no-op or Forge events. `CustomNPCs JAR!/noppes/npcs/api/entity/ICustomNpc.class`

`NpcAdapters.resolve` should continue conservative composition. One highest-priority framework provider supplies `frameworkId`, progression, mana scale, traits, and equipment mutation; all applicable adapters may veto activity/targets, declare allies, and restrict movement. This keeps CustomNPC factions additive with scoreboard teams, ownership, raid allies, and pets. `src/main/java/com/otectus/magicnpcs/core/adapter/NpcAdapters.java`

### 6.2 Detection and binding lifecycle

1. During Magic NPCs construction, a neutral `CustomNpcsCompat` reads `ModList.get().isLoaded("customnpcs")` and the mod-file version string. It contains no `noppes.*` field, method signature, annotation, static initializer, or class literal. Magic NPCs already uses guarded neutral compat facades for optional frameworks. `src/main/java/com/otectus/magicnpcs/MagicNpcs.java`, `src/main/java/com/otectus/magicnpcs/compat/EasyNpcCompat.java`, `src/main/java/com/otectus/magicnpcs/compat/IronsCompat.java`
2. If absent, status becomes `ABSENT` and no typed class is loaded.
3. If present but not allow-listed, status becomes `DISABLED_INCOMPATIBLE`; emit one error identifying detected and verified versions, and do not reflectively load the typed module.
4. If allow-listed, reflectively load a no-argument typed entry point under `compat/customnpcs/`. That entry point probes `NpcAPI.Instance()`, `events()`, `getIEntity`, `ICustomNpc`, `INPCAi`, `INPCInventory`, `IFaction`, `trigger`, and the event classes before registering anything. These members are present in the pinned JAR. `CustomNPCs JAR!/noppes/npcs/api/NpcAPI.class`, `CustomNPCs JAR!/noppes/npcs/api/entity/ICustomNpc.class`, `CustomNPCs JAR!/noppes/npcs/api/entity/data/INPCAi.class`, `CustomNPCs JAR!/noppes/npcs/api/entity/data/INPCInventory.class`
5. After a successful probe, register `CustomNpcsAdapter` in `NpcAdapters`, register the bridge object on `NpcAPI.events()` (the **CustomNPCs API bus**), and register neutral server cleanup/diagnostic hooks on the **Forge bus**. `CustomNPCs JAR!/noppes/npcs/api/NpcAPI.class`, `src/main/java/com/otectus/magicnpcs/core/adapter/NpcAdapters.java`
6. Any `LinkageError`, reflection exception, or probe mismatch tears down partial bridge state, reports `DISABLED_ERROR`, and leaves all non-CustomNPC Magic NPCs features active.

The bridge must be initialized only once and must unregister/clear external UUID state on server stop. Magic NPCs already clears managed caster state on `ServerStoppedEvent` on the **Forge bus**. `src/main/java/com/otectus/magicnpcs/MagicNpcs.java`, `src/main/java/com/otectus/magicnpcs/core/caster/ManagedCasterState.java`

### 6.3 Managed-CustomNPC lifecycle and AI repair

The bridge reacts to `NpcEvent.InitEvent` and `NpcEvent.UpdateEvent` on the **CustomNPCs API bus**. It obtains the vanilla `Mob` through `event.npc.getMCEntity()`, validates that the entity is server-side/alive, and performs a read-only eligibility check before touching Magic data. `CustomNPCs JAR!/noppes/npcs/api/event/NpcEvent.class`, `CustomNPCs JAR!/noppes/npcs/api/entity/IEntity.class`, `CustomNPCs JAR!/noppes/npcs/EventHooks.class`

For an unmanaged NPC, the update listener returns in constant time and does not create Forge data. For a managed caster, it checks whether exactly one Magic NPCs casting goal and the expected optional movement/suppression state are present. If intact, it returns. If missing, it asks `CasterReconciler` to reconcile with a new `CUSTOMNPCS_AI_REBUILD` reason. The current reconciler already removes/adds only its own goals and can reapply native suppression when its runtime state says suppression is active but wrapper goals are absent. `src/main/java/com/otectus/magicnpcs/integration/irons/CasterReconciler.java`, `src/main/java/com/otectus/magicnpcs/core/caster/ReconcileReason.java`, `src/main/java/com/otectus/magicnpcs/core/util/AttackGoals.java`

Reconciliation must be idempotent and deduplicated per entity/tick. If the API event is proven to occur during unsafe selector iteration, the listener enqueues the UUID into the existing bounded server-tick reconciliation queue rather than mutating immediately; the acceptance test, not conjecture, decides this. `src/main/java/com/otectus/magicnpcs/integration/irons/IronsSpellcasterHandler.java`

No competing target goal is added. CustomNPCs retains responsibility for choosing/changing the `Mob` target and fires its cancelable target events; Magic NPCs reads the resulting target and applies its own last-mile friendly-fire gate. `CustomNPCs JAR!/noppes/npcs/entity/EntityNPCInterface.class`, `CustomNPCs JAR!/noppes/npcs/api/event/NpcEvent$TargetEvent.class`, `src/main/java/com/otectus/magicnpcs/integration/irons/NpcSpellAttackGoal.java`

### 6.5 Reverse direction: CustomNPCs sees and drives magic

The bridge exposes a server-only `MagicNPCs` script facade with operations conceptually named `isCaster`, `getSchool`, `getLoadout`, `getMana`, `getMaxMana`, `canCast`, `setSchool`, `clearSchool`, `returnToAuto`, `setCastingSuspended`, `cast`, and `why`. Every mutating operation validates side, entity liveness, script-mutation config, school/spell allow-lists, cooldown/mana, and friendly-fire rules; it returns a structured result code rather than throwing into the script engine. CustomNPC server scripts are trusted pack content, not players or Brigadier sources, so the bridge must not invent a command source or pretend command permission levels apply. Existing Magic NPCs has the underlying school mutation, detached cast, diagnostics, and loadout resolution paths to call. `src/main/java/com/otectus/magicnpcs/integration/irons/IronsSpellcasterHandler.java`, `src/main/java/com/otectus/magicnpcs/integration/irons/DetachedCastDriver.java`, `src/main/java/com/otectus/magicnpcs/integration/irons/CasterDiagnostics.java`, `src/main/java/com/otectus/magicnpcs/core/loadout/LoadoutManager.java`

For the pinned build only, an optional reflective installer may put that facade into internal `ScriptContainer.Data` under the exact key `MagicNPCs`, producing the ergonomic script global. Failure disables only that convenience layer. `ScriptContainer.Data` is internal and seeds script engines in the supplied JAR. `CustomNPCs JAR!/noppes/npcs/controllers/ScriptContainer.class`

The public fallback and interoperability contract is a stored-data mailbox plus triggers:

- Request keys are namespaced `magicnpcs.request.v1.*`; result keys are `magicnpcs.result.v1.*` and contain only strings/numbers, matching stored-data constraints. `CustomNPCs JAR!/noppes/npcs/api/entity/IEntity.class`, `CustomNPCs JAR!/noppes/npcs/api/entity/data/IData.class`, `CustomNPCs JAR!/noppes/npcs/api/wrapper/EntityWrapper.class`
- A server-side CustomNPC script writes a request and invokes its chosen integration entry; the bridge processes it at the next `NpcEvent.UpdateEvent` and writes the result.
- Magic NPCs signals call `ICustomNpc.trigger(configuredId, npcWrapper, "magicnpcs:v1", signalName, payload...)`. The wrapper is passed explicitly because the internal world-event construction used by custom triggers does not reliably supply an entity field. `CustomNPCs JAR!/noppes/npcs/api/entity/ICustomNpc.class`, `CustomNPCs JAR!/noppes/npcs/api/wrapper/NPCWrapper.class`, `CustomNPCs JAR!/noppes/npcs/api/event/WorldEvent.class`
- Scripts must reject a trigger whose string prefix/version is not exactly `magicnpcs:v1`; the raw integer is configurable to avoid user-pack collisions.

Magic NPCs should also publish framework-neutral Forge events—`MagicNpcCastPre` (cancelable), `MagicNpcCastStarted`, `MagicNpcCastCompleted`, `MagicNpcCastCancelled`, and `MagicNpcSchoolChanged`—on the **Forge bus** using only vanilla/Magic NPCs types. The CustomNPC bridge listens to those events on the **Forge bus** and translates them to `ICustomNpc.trigger`; no CustomNPC type appears in the event classes.

CustomNPC dialogue options, quest completion handlers, faction scripts, role scripts, timers, and generic custom triggers can then call the same facade/mailbox. The bridge should not automatically complete quests, open dialogs, alter factions, or choose role/job values: those semantics remain script/pack authored.

This is a conditional presentation bridge, not a new item/alias; compare the tab key and accept the already-registered `magicnpcs:school_tome`. `src/main/java/com/otectus/magicnpcs/registry/MagicNpcsItems.java`, `CustomNPCs JAR!/noppes/npcs/CustomTabs.class`

## 7. Compat Layer Implementation Strategy

### 7.1 Package and classloading boundary

Recommended package ownership:

- `com.otectus.magicnpcs.compat.CustomNpcsCompat` — neutral detection/status/bootstrap; **must not** import, extend, annotate with, return, accept, or hold any `noppes.*` type.
- `com.otectus.magicnpcs.compat.customnpcs.CustomNpcsIntegration` — typed entry point loaded only by name after detection/version checks.
- `compat.customnpcs.CustomNpcsAdapter` — public-API-backed `NpcAdapter`/`MagicNpc` provider.
- `compat.customnpcs.CustomNpcsEventBridge` — listeners for the CustomNPCs API bus and translation to/from neutral Magic events.
- `compat.customnpcs.CustomNpcsAiRepair` — managed-goal invariant check and deduplication.
- `compat.customnpcs.CustomNpcsInventoryBridge` — `IItemStack` conversion and authoritative hand update.
- `compat.customnpcs.CustomNpcsScriptBridge` — public mailbox/trigger bridge and optional internal-global probe.
- `compat.customnpcs.CustomNpcsDiagnostics` — detected version, probe health, event count, repairs, failures, and active fallbacks.
- `compat.customnpcs.client.*` — reserved; no `0.8.0` class is needed there.

Only classes under `compat/customnpcs/` may directly reference `noppes.npcs.api.*`. Nothing there may be named in `MagicNpcs` fields/method descriptors or annotations; the neutral bootstrap invokes a neutral no-argument interface or reflective static entry point. `MagicNpcs`, core adapter/loadout classes, Iron's integration, registries, commands, and data generation remain CustomNPC-free. This follows the existing guarded optional-mod shape, where common code asks neutral compat facades before reaching dependency-typed implementations. `src/main/java/com/otectus/magicnpcs/MagicNpcs.java`, `src/main/java/com/otectus/magicnpcs/compat/EasyNpcCompat.java`, `src/main/java/com/otectus/magicnpcs/compat/easynpc/EasyNpcIntegration.java`

Add an automated constant-pool/class-reference check: when the CustomNPC fixture is absent, no class outside `compat/customnpcs/` may contain `noppes/npcs/`, and the neutral bootstrap itself must not. This catches seemingly harmless generic signatures, annotations, static fields, or exception types that would defeat the runtime guard.

### 7.2 Compile-time dependency versus reflection

Recommendation: use a **hybrid** boundary.

- Compile the typed leaf module against the exact supplied JAR as `compileOnly fg.deobf(...)`; never shade, jar-in-jar, publish, or transitively expose it. Stage it through the existing `flatDir` repository as a named local coordinate rather than `files(...)`, because this build already documents that ForgeGradle cannot deobfuscate-remap the self-resolving form. This gives compiler checking for the intended public API and readable typed adapter/event code. Magic NPCs already uses `compileOnly fg.deobf` for Iron's and Easy NPC and an optional local `fg.deobf` JAR for Recruits. `build.gradle`, `gradle.properties`
- Add the exact CustomNPCs JAR only to an explicit development/test runtime profile. The production Magic NPCs artifact must contain no CustomNPC classes/resources.
- Record artifact filename, implementation version `1.20.1.20260711`, and SHA-256 in build documentation/a verification task. Because U-10 lacks a reproducible coordinate, fail the compat compile with an actionable missing-fixture message rather than silently omitting typed sources.
- Use reflection in the neutral bootstrap so CustomNPCs' absence prevents typed leaf verification/loading, and for the optional internal `ScriptContainer.Data` global injection. Do **not** reflect every public API call: that would trade compiler guarantees for stringly typed, slower, harder-to-review code without fixing semantic drift.

Tradeoff: a compile-only public API still permits runtime `NoSuchMethodError` on an incompatible JAR, while reflection can probe and isolate it. The exact-version gate and catch-all `LinkageError` boundary address that risk; public operational code remains typed and internal access remains reflective.

### 7.3 `mods.toml` and runtime version contract

Add a `mandatory=false`, `ordering="AFTER"`, `side="BOTH"` dependency entry for mod ID `customnpcs`. Its metadata range should admit 1.20.1 builds rather than pretending that all are ABI-compatible; `[1.20.1,1.21)` is the recommended descriptive range. Runtime verification—not Forge dependency resolution—decides whether compat activates. Existing optional dependencies use `mandatory=false`, `AFTER`, and `BOTH`. `src/main/resources/META-INF/mods.toml`

The initial exact allow-list contains only `1.20.1.20260711`. At runtime record:

- `ABSENT` — mod not installed;
- `PRESENT_UNSUPPORTED` — installed version not allow-listed;
- `PROBE_FAILED` — allow-listed version but required API member/bus unavailable;
- `ACTIVE_PUBLIC_API` — adapter/event/mailbox bridge active;
- `ACTIVE_FULL` — public bridge plus optional script global active;
- `DEGRADED_AI_REPAIR` — event repair failed and an approved fallback is active;
- `DISABLED_ERROR` — an operational linkage/runtime fault disabled the compat session.

Unknown builds must not “best effort” cast. Log one `ERROR` containing detected version, verified version(s), failed probe/member, and a command to inspect status. Rate-limit per-entity operational faults; after a small threshold, open the per-session circuit breaker and disable the bridge rather than flooding logs or repeatedly risking tick failure.

`/magicnpcs config` and `/magicnpcs why <target>` should report compat status, detected/verified versions, public API probe, event-bus registration, last update-event age, repair count, duplicate-goal count, script-global/mailbox status, and any active safety veto. Existing diagnostics already expose loadout/adapter/reconcile information and accept contributors. `src/main/java/com/otectus/magicnpcs/command/ConfigCommand.java`, `src/main/java/com/otectus/magicnpcs/command/WhyCommand.java`, `src/main/java/com/otectus/magicnpcs/core/diag/DiagnosticContributors.java`

### 7.4 Mixins: baseline and fallback

No Magic NPCs mixin is justified for the baseline. The required hook already exists as the public `NpcEvent.UpdateEvent`, emitted after the entity's superclass tick in the inspected build, and the current reconciler can restore missing goals without reaching a private field/method. `CustomNPCs JAR!/noppes/npcs/entity/EntityNPCInterface.class`, `CustomNPCs JAR!/noppes/npcs/EventHooks.class`, `src/main/java/com/otectus/magicnpcs/integration/irons/CasterReconciler.java`

Only if U-02 proves the event hook cannot safely/quickly repair should Milestone 5 consider a fallback mixin:

- Target the exact pinned `EntityNPCInterface.updateTasks()` at `TAIL`, server only.
- Do not reconcile inside the private method; enqueue the entity UUID for the next server tick to avoid selector mutation reentrancy.
- Put it in a separate compat mixin JSON controlled by an `IMixinConfigPlugin` that checks mod presence and exact version before target selection.
- Use `require = 0` and an explicit runtime heartbeat. If the target changes or the injection is not observed, log and disable only CustomNPC compat.
- Do not shadow CustomNPC fields and do not mix an interface into its entity.

This mixin is preferable only to an unconditional all-world scan if the public event fails: it observes the exact destructive operation and has O(rebuilds) cost. Its failure mode is a renamed/reshaped private method after a CustomNPC update; the version gate and heartbeat turn that into visible compat disablement rather than a crash or silent half-integration.

### 7.7 Failure isolation and cleanup

The bridge may maintain external UUID sets only for ephemeral facts that have no owner elsewhere: active dialogue/edit suspension, update-event heartbeat, per-tick repair deduplication, and fault counters. Remove entries on `EntityLeaveLevelEvent` on the **Forge bus**, clear all on `ServerStoppedEvent` on the **Forge bus**, and prune stale UUIDs without scanning worlds. Existing Magic NPCs uses the same entity-leave/server-stop lifecycle for managed casting state. `src/main/java/com/otectus/magicnpcs/integration/irons/IronsSpellcasterHandler.java`, `src/main/java/com/otectus/magicnpcs/MagicNpcs.java`

After activation, every entry point catches incompatibility failures at the typed-module boundary and opens a single session circuit breaker. It must not catch ordinary gameplay exceptions so broadly that Magic NPCs defects are hidden; diagnostics should retain the first stack trace and a short failure reason.

### 8.2 Role, job, and movement mapping

Centralize the pinned integer map in one compat class and cover it with fixture tests. The supplied implementation maps roles `1..7` to trader, follower, bank, transporter, postman, companion, and dialog, and jobs `1..11` to bard, healer, guard, item giver, follower, spawner, conversation, chunk loader, puppet, builder, and farmer. `CustomNPCs JAR!/noppes/npcs/entity/data/DataAdvanced.class`, `CustomNPCs JAR!/noppes/npcs/api/entity/data/INPCRole.class`, `CustomNPCs JAR!/noppes/npcs/api/entity/data/INPCJob.class`

The traits exposed to datapacks are identifiers, never localized display names:

- `customnpcs:role/none`, `/trader`, `/follower`, `/bank`, `/transporter`, `/postman`, `/companion`, `/dialog`;
- `customnpcs:job/none`, `/bard`, `/healer`, `/guard`, `/item_giver`, `/follower`, `/spawner`, `/conversation`, `/chunk_loader`, `/puppet`, `/builder`, `/farmer`;
- `customnpcs:faction/<decimal-id>`;
- `customnpcs:movement/stationary`, `/wander`, or `/path`;
- `customnpcs:navigation/ground`, `/flying`, or `/swimming`.

Add a loadout condition `npc_traits` with `all_of`, `any_of`, and `none_of` arrays. Parsing remains vanilla-only and treats identifiers opaquely; runtime evaluation asks the resolved `MagicNpc`. That keeps the core JSON layer free of CustomNPC classes, consistent with existing context condition separation. `src/main/java/com/otectus/magicnpcs/core/loadout/LoadoutConditions.java`, `src/main/java/com/otectus/magicnpcs/core/loadout/LoadoutParser.java`

Retaliation values `0..3` in the pinned API mean fight, panic, avoid, and no-response according to the goal-building branches. Only `0` permits attack spellcasting by default; the other three still permit configured self-support unless blocked by dialogue/job/freeze/global state. `CustomNPCs JAR!/noppes/npcs/entity/data/DataAI.class`, `CustomNPCs JAR!/noppes/npcs/entity/EntityNPCInterface.class`

Moving type `0` adds no wander/path goal, `1` adds `EntityAIWander`, and `2` adds `EntityAIMovingPath`. Map them to `PINNED`, `ANCHORED(home, wanderingRange)`, and `PINNED`, respectively, so Magic NPCs never pulls an NPC off an authored path. `CustomNPCs JAR!/noppes/npcs/entity/EntityNPCInterface.class`, `CustomNPCs JAR!/noppes/npcs/api/entity/data/INPCAi.class`, `src/main/java/com/otectus/magicnpcs/core/adapter/NpcAdapter.java`

### 8.3 Casting, cancellation, and signal ordering

For one cast attempt, ordering is:

1. Resolve current `MagicNpc`; reject activity/target/mana/cooldown/LOS/line-of-fire failures using existing spell diagnostics. `src/main/java/com/otectus/magicnpcs/integration/irons/NpcSpellAttackGoal.java`, `src/main/java/com/otectus/magicnpcs/core/SpellDiagnostic.java`
2. Post cancelable `MagicNpcCastPre` on the **Forge bus**. A cancellation records an explicit reason and emits a CustomNPC `cast_cancelled` signal; it does not spend mana/start cooldown.
3. Start windup/session and post `MagicNpcCastStarted` on the **Forge bus**; translate to `magicnpcs:v1` CustomNPC trigger. `src/main/java/com/otectus/magicnpcs/integration/irons/MobCastSession.java`, `src/main/java/com/otectus/magicnpcs/core/feedback/Telegraphs.java`
4. Immediately before commit, repeat liveness, activity, target, and friendly-fire checks because CustomNPC scripts can change target/faction during windup. `CustomNPCs JAR!/noppes/npcs/api/event/NpcEvent$TargetEvent.class`, `src/main/java/com/otectus/magicnpcs/integration/irons/NpcSpellAttackGoal.java`
5. On commit, use the existing Iron's cast driver and cooldown/mana semantics; post `Completed` only when the cast reaches its success point. `src/main/java/com/otectus/magicnpcs/integration/irons/MobCastSession.java`, `src/main/java/com/otectus/magicnpcs/integration/irons/DetachedCastDriver.java`
6. Any target loss, dialogue pause, death, goal rebuild, or script cancellation stops the session through the existing cancellation path, clears telegraph state, and emits exactly one terminal signal. `src/main/java/com/otectus/magicnpcs/integration/irons/CasterReconciler.java`, `src/main/java/com/otectus/magicnpcs/core/feedback/Telegraphs.java`

Custom triggers are notifications, not a second cancellation protocol. For advanced packs, permit a pre-cast script to place `magicnpcs.cancel.v1 = 1` in **temporary** data during the synchronous trigger, then remove/read it immediately; this is optional and separately configurable because the public `trigger` method has no return value. `CustomNPCs JAR!/noppes/npcs/api/entity/ICustomNpc.class`, `CustomNPCs JAR!/noppes/npcs/api/entity/IEntity.class`

## 9. Milestones & File-Level Change Plan

Each milestone produces a bootable artifact and keeps CustomNPCs optional. No change is planned against the third-party JAR.

### Milestone definitions

1. **M1 — Prove typed soft-dep and goal repair.** Smallest useful slice: exact-version bootstrap, minimal adapter, manual/explicit caster support, Custom API update listener, idempotent goal repair, absence/incompatibility behavior, and diagnostics. No factions, traits, auto schools, inventory bridge, or scripting. This artifact is independently bootable but keeps `customnpcs.bridgeEnabled=false` outside the controlled test profile because framework-specific safety is not complete. Exit only when U-02 is resolved on integrated and dedicated servers.
2. **M2 — Make combat semantics safe.** Introduce resolved `MagicNpc`, faction/owner/activity/role/job/movement policy, native-goal repair, and dialogue suspension. This makes an explicit CustomNPC caster respect its authored system.
3. **M3 — Complete authoring/content integration.** Add traits/conditions, CustomNPC school policy, authoritative inventory writes, conditional creative-tab listing, clone/linked behavior documentation, and examples.
4. **M4 — Expose bidirectional events and scripting.** Add neutral Magic Forge events, Custom trigger translation, public mailbox, optional exact-build script global, result codes, and script examples.
5. **M5 — Harden and release `0.8.0`.** Version/constant-pool checks, compatibility matrix, performance/load testing, world upgrades, release docs, and only if M1 evidence requires it, the optional AI-rebuild fallback mixin.

## 12. Non-Goals & Deferred

- **No CustomNPCs code changes.** This plan treats the supplied JAR as fixed and lands all changes in Magic NPCs.
- **No automatic conversion of all CustomNPCs NPCs.** Installation alone creates zero new casters; direct entity-type loadouts and automatic schools require explicit opt-in.
- **No replacement/merger of entity types.** Magic NPCs will not register a unified NPC entity, convert CustomNPC NBT to a Magic entity, or make vanilla/third-party entities implement an interface through mixins.
- **No baseline CustomNPC mixin.** The public API event is the planned repair hook. The narrow private-tail fallback is deferred until U-02 produces evidence that it is required.
- **No new bridge capability or duplicate mana store.** School/loadout entity data, Iron's mana, Magic runtime state, and CustomNPC authoring data retain their existing owners. `src/main/java/com/otectus/magicnpcs/core/SchoolData.java`, `src/main/java/com/otectus/magicnpcs/core/caster/ManagedCasterState.java`, `CustomNPCs JAR!/noppes/npcs/entity/EntityNPCInterface.class`
- **No new network channel, menu, screen, renderer, layer, model, or keybind in `0.8.0`.** Existing server casting feedback and both mods' channels/client systems remain separate. `src/main/java/com/otectus/magicnpcs/core/feedback/Telegraphs.java`, `CustomNPCs JAR!/noppes/npcs/packets/Packets.class`
- **No automatic quest/dialog/faction/role/job mutation.** Those systems can query/drive Magic through scripts and events, but Magic NPCs will not decide narrative progression or NPC occupation.
- **No inferred editor, trade, or scene-active state.** The pinned public API exposes dialog events but no general active-state accessor; authors use explicit transient script suspension for those workflows. `CustomNPCs JAR!/noppes/npcs/api/event/DialogEvent.class`, `CustomNPCs JAR!/noppes/npcs/api/entity/ICustomNpc.class`
- **No direct parsing or writing of CustomNPC controller, clone, linked, playerdata, or external-pack files.** Integration operates through entity state and public API.
- **No internal owner UUID, scene, role/job implementation, packet, controller, or entity-field dependency.** Offline-owner inference is deferred until a public API exists.
- **No support claim for an older/newer CustomNPCs build merely because it loads.** Each build requires fixture pin, probes, and the full compatibility matrix.
- **No fix to CustomNPCs' own `pack.mcmeta`, common/client mixins, server-side classloading, or removal behavior.** Those are third-party issues to characterize and document, not patch from Magic NPCs.
- **No bundled CustomNPCs JAR or assets.** The binary is a compile/test fixture only unless its rights holder explicitly authorizes redistribution.
- **No implicit use of command execution as an API.** Although `ICustomNpc.executeCommand` exists, the script bridge calls Magic services directly and returns typed/result-code outcomes. `CustomNPCs JAR!/noppes/npcs/api/entity/ICustomNpc.class`
- **Deferred:** a CustomNPC editor tab for schools/loadouts, visual skin/model-aware cast layers, persistent offline-owner resolution, first-class scene schedule hooks, quest objectives based on spell events, and upstreaming a stable public AI-rebuild event. Each adds client/internal or narrative coupling not needed to prove coherent core behavior.

## 13. Open Questions

Each question includes the recommended default; approving the defaults as a set is sufficient.

1. **Which CustomNPC build is a release target?** Recommended: support only `1.20.1.20260711` in `0.8.0`; treat every other version as detected-but-disabled until it passes Section 10.
2. **Should the compat bridge activate automatically when the exact build is present?** Recommended: yes for adapter/repair/manual-school/script infrastructure, but keep `compat.customnpcs=false` for direct entity-namespace loadouts and `schools.customnpcs.enabled=false` for automatic casters. This yields safety without surprising content changes.
3. **Should manual School Tome/command assignment bypass the namespace loadout toggle?** Recommended: yes. The user's explicit per-entity action is stronger intent than an installation-level bulk-loadout toggle; faction/activity protections still apply.
4. **How should native attacks coexist?** Recommended: default examples to `coexist`; authors choose `yield` or `suppress` per loadout. Never force `suppress` for all CustomNPCs.
5. **What should happen during dialogue?** Recommended: cancel/pause both attack and support casts while a dialog/interaction is active, then resume eligibility without clearing cooldown. It protects narrative interactions from visual/combat interruption.
6. **Which roles/jobs should be blocked by default?** Recommended: only jobs `puppet` and `builder`; no blocked roles. Explicit loadout opt-in plus fight-mode/faction gates handle the rest.
7. **How should stationary/path/follower movement behave?** Recommended: `PINNED`; wanderers are anchored to CustomNPC home/range. Magic should lose a cast opportunity rather than disobey authored movement.
8. **What faction rule should neutral mean?** Recommended: neutral neither grants hostility nor automatic alliance; defer to vanilla/team/owner/other adapters. Same/friendly protects; explicit hostile permits target consideration.
9. **Should the bridge use internal owner data to protect offline-owner siblings?** Recommended: no. Accept/document the public API limitation rather than pinning another internal field.
10. **Should clones inherit Magic state?** Recommended, subject to U-03: full clones copy explicit/manual school and persistent loadout/equipment marks because those are part of the authored NPC; they never copy cooldown/channel/dialog runtime state. Linked templates keep Magic state per instance.
11. **Should a reflective `MagicNPCs` script global be enabled?** Recommended: yes for the exact build, with an independent switch and public mailbox/trigger as the guaranteed fallback.
12. **Which trigger ID should ship?** Recommended: `8800`, configurable, with mandatory `magicnpcs:v1` payload prefix. CustomNPCs exposes no reserved-ID registry in the inspected public API, so documentation must tell pack authors how to change it. `CustomNPCs JAR!/noppes/npcs/api/entity/ICustomNpc.class`
13. **Should Custom scripts be able to cancel a cast?** Recommended: normal Forge listeners can cancel `MagicNpcCastPre`; CustomNPC scripts may opt into the synchronous temporary-data handshake, off only if a pack reports collisions/performance issues. Do not overload the stored mailbox for same-tick cancellation.
14. **May CustomNPC server scripts mutate Magic state?** Recommended: yes by default because they are trusted pack content, behind `scriptMutationsEnabled`; disabling it leaves all queries and outgoing events available. Never execute a command or fabricate a player permission context.
15. **How much repair latency is acceptable?** Recommended: same tick when proven safe, otherwise a deduplicated next-server-tick queue (≤1 tick). Do not add a private mixin merely to remove one tick of latency.
16. **Should Magic NPCs modify CustomNPCs files or external resource pack?** Recommended: no. Ship all data under `magicnpcs` and use API/entity state only.
17. **Should unsupported CustomNPC builds best-effort enable public pieces?** Recommended: no for `0.8.0`. Log exact incompatibility and stay disabled; add versions deliberately after testing.

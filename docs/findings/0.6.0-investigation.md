# 0.6.0 — Phase 1 investigation findings

**Method.** Every claim below was verified against bytecode/sources in the local ForgeGradle caches, not
from memory:

- Minecraft/Forge 1.20.1: `forge-1.20.1-47.4.16_mapped_official_1.20.1-sources.jar`
  (`minecraft_user_repo`), official mappings — the exact sources this project compiles against.
- Iron's Spells 'n Spellbooks 3.15.2: `irons-spells-n-spellbooks-855414-7402504_mapped_official_1.20.1.jar`
  (`deobf_dependencies`), read with `javap -c -p`.

Each finding names the file and the decisive line so it can be re-checked.

## W1 — SUPPORT spells never cast outside combat · **CONFIRMED**

`NpcSpellAttackGoal.canUse()` returned `false` whenever `mob.getTarget()` was null, before any role
check. Everything downstream was already target-optional (`choose()` passes `null` for SUPPORT
conditions, `windupTargetValid()` short-circuits for non-ATTACK roles, `SchoolSpellPool` gives SUPPORT
entries `max_range = 0`), so the single target gate was the whole bug.

**Is a target-less self-heal actually safe for Iron's?** Yes. `HealSpell.onCast` (Iron's 3.15.2)
decompiles to:

```
 3: invokevirtual getSpellPower:(ILnet/minecraft/world/entity/Entity;)F
…
32: aload_3                                  // the LivingEntity caster parameter
33: fload 6
35: invokevirtual net/minecraft/world/entity/LivingEntity.heal:(F)V
```

It heals **the caster passed to `onCast`** and reads no `TargetEntityCastData`. `SpellCompat.categoryOf`
already classifies it as `DIRECT_PROJECTILE_OR_SIMPLE_SELF`, and `IronsBridge.cast` only demands a target
for `TARGET_ENTITY_REQUIRED`. So a SUPPORT cast with `target == null` is well-defined.

**Decision:** self-only support out of combat in 0.6.0; ally-targeted support is deliberately deferred
(see ADR 0005).

## W2 — Mobs with native ranged AI never cast · **CONFIRMED (mechanism), per-mob results vary**

The mechanism is a `GoalSelector` flag/priority conflict, and it is exact:

`WrappedGoal.canBeReplacedBy` (`net/minecraft/world/entity/ai/goal/WrappedGoal.java:16-18`):

```java
public boolean canBeReplacedBy(WrappedGoal p_26003_) {
   return this.isInterruptable() && p_26003_.getPriority() < this.getPriority();
}
```

`GoalSelector.tick()` (`GoalSelector.java:101-111`) only starts a non-running goal when
`goalCanBeReplacedForAllFlags(...)` holds for **every** flag the candidate declares. A goal that
declares **no** flags iterates zero flags and therefore always passes that gate.

- **`minecraft:witch`** (`Witch.java` `registerGoals`): `this.goalSelector.addGoal(2, new RangedAttackGoal(this, 1.0D, 60, 10.0F));`
  `RangedAttackGoal`'s constructor calls `setFlags(EnumSet.of(Goal.Flag.MOVE, Goal.Flag.LOOK))`
  (`RangedAttackGoal.java:39`), and its `canUse()` is true whenever the witch has a live target.
  Our goal was injected at priority **2** with `EnumSet.of(Flag.LOOK)` ⇒ `2 < 2` is false ⇒ the witch's
  goal owns the LOOK lock for as long as it has a target ⇒ **our goal can never start**. Exactly the
  reported symptom.
- **`AbstractSkeleton`** (`AbstractSkeleton.java` `reassessWeaponGoal`): the bow goal is added at
  priority **4**. `2 < 4` is true ⇒ our goal *stops the bow goal* and takes the LOOK lock every time it
  is ready. The skeleton was casting *instead of* shooting — the other half of W3.

One root cause, two opposite-looking outcomes, as the brief predicted.

**Note on priority semantics.** `GoalSelector.tick()` iterates `availableGoals` in *insertion* order, not
priority order; priority is consulted **only** by `canBeReplacedBy`, i.e. only for flag contention. With
no flags declared, the injection priority is therefore almost inert — which is why the fix is primarily
about flags, and `castingGoalPriority` exists for the `suppress`/`yield` cases and for mods whose goals
declare flags we do want to preempt.

**Luminous Monsters (phoenix / witch doctor):** not installable in this dev environment, so no runtime
result was obtained. They are addressed structurally rather than by guesswork: `/magicnpcs why` now dumps
every `WrappedGoal` with priority/flags/running state and flags the blocking goal by class, so the answer
is one command for any mob from any mod. If those mobs turn out not to tick `goalSelector` at all
(GeckoLib/animation-state or Brain-based attack logic), no priority or flag change can help them; that is
documented as a limitation in `README.md` rather than left silently broken.

## W3 — Skeleton frequency and no way to disable a loadout

**(a) shipped skeleton loadout** — already removed in 0.5.0 (`SpellcasterLoadoutProviderTest` guards it).
Nothing to build.

**(b) cooldowns ran at ~half the configured rate** · **CONFIRMED.**
`Mob.serverAiStep()` (`Mob.java:742-762`):

```java
int i = this.level().getServer().getTickCount() + this.getId();
if (i % 2 != 0 && this.tickCount > 1) {
   this.targetSelector.tickRunningGoals(false);
   this.goalSelector.tickRunningGoals(false);      // <- canUse() is NOT reached
} else {
   this.targetSelector.tick();
   this.goalSelector.tick();                        // <- canUse() only here
}
```

`canUse()` — which is where `tickCooldowns()` and `decisionTimer--` lived — therefore runs on **every
other game tick**. A configured `minCooldownTicks = 20` was really ≈40 game ticks, and
`CooldownResolver`'s documented "20 ticks = 1 second" did not correspond to game time.

Note the asymmetry that made this hard to spot: `requiresUpdateEveryTick()` returns true, so
`tickRunningGoals(false)` *does* tick a running goal every tick — the wind-up countdown was already in
real ticks while the cooldown/decision counters were not.

**Fix:** both counters became `mob.tickCount`-based deadlines. Because `canUse()` is still only evaluated
on alternating ticks, a deadline is honoured to within one tick — documented, not papered over.

**Consequence:** every existing pack's casters get roughly **twice as fast** unless they re-tune. Called
out under Migration in `CHANGELOG.md`.

**(c) no disable mechanism** · **CONFIRMED.** `LoadoutManager.parse` threw `"loadout has no spells"`, so
even the `"replace": true` + empty-list trick was unavailable. Fixed by a root-level `"enabled": false`
plus `general.disabledEntityTypes`.

## W4 — `school reroll` reports "0 NPCs" · **CONFIRMED, two compounding bugs**

1. `SchoolCommand.reroll` picked **one** random school per mob and reported only the success count, with
   no reason and no retry. A school that yields no castable spells produced
   `Re-rolled schools for 0 NPC(s)` with zero information — and because the pick was random per
   invocation, the same command succeeded or failed run to run. That is precisely the reporter's
   "schools come and go".
2. `SchoolSpellPool.buildLoadout` returned `null` for a whole school when its filters emptied the
   candidate list. The dominant filter was `spell.getCastType() != CastType.INSTANT`, which excluded
   every `LONG` spell — even though 0.5.0 taught the goal to channel `LONG` casts correctly
   (`resolveWindup` → `IronsBridge.castTime`, `IronsBridge.cast` → `onServerCastComplete`). The pool was
   filtering out spells the goal already handles.

Verified on the Iron's side: `SpellRegistry.getSpellsForSchool` does **not** filter disabled spells — it
is a plain `computeIfAbsent` over `REGISTRY.get().getValues()` filtered by school only — so the explicit
`isEnabled()` check in the pool is required, and a school whose spells are all disabled in Iron's config
legitimately yields nothing.

**Fixes:** `SchoolAssignResult` (Iron's-free) replaces the boolean; `reroll` walks the whole shuffled
allowed pool and reports per-school reasons; `schools.allowedCastTypes` defaults to `["INSTANT","LONG"]`;
`/magicnpcs school pool` prints per-filter survivor counts; a one-line-per-school summary is logged on
reload.

Also fixed here: a mob with a **stored** school whose `buildLoadout` now returns `null` (caps tightened
after assignment) injected no goal but was still treated as a school caster by `onLivingTick`, which
regenerated its mana forever.

## W5 — Config is server-only · **CONFIRMED**

`MagicNpcs.java:39` registered exactly one spec, `ModConfig.Type.SERVER`. That is correct for per-world
gameplay balance but gives a modpack author no pack-level default without the `defaultconfigs/` trick.

**Side audit.** Every config read in the tree runs server-side: `Telegraphs` early-returns unless
`caster.level() instanceof ServerLevel`; the goal, handler, loadout manager, commands and school code are
all server-thread. **No CLIENT spec is warranted** and none was added — the reporter's phrase "not
client" describes the symptom (no pack-level default), not the fix.

## W6 — Author's JSON loses to the shipped loadout · **CONFIRMED**

`src/generated/resources/data/magicnpcs/spellcasters/guard.json` ships an **active**
`guardvillagers:guard` loadout with `magic_missile` + `guiding_bolt` + `heal` — literally the "magic bolt
and other stuff" in the report. A pack author's own guard JSON has a different file id, so
`LoadoutManager.resolve` **pooled** the two and sticky-picked one per NPC by `pool_weight`: some guards
used theirs, some used ours, permanently.

**Verified mechanism for the fix.** Mod-jar data packs are `PathPackResources` constructed with
`isBuiltin = true` (`ResourcePackLoader.createPackForMod`), and Forge registers one server-data `Pack`
per mod file from that object (`ServerLifecycleHooks.buildPackFinder`). `Resource.sourcePackId()` /
`Resource.isBuiltin()` therefore identify jar-shipped data without string-matching a namespace — which
matters because a datapack may legitimately use the `magicnpcs:` namespace. See ADR 0003.

## Backlog items re-verified before fixing

- **B1** `SchoolData.root()` was a mutating getter — it `put`s an empty `magicnpcs{}` compound on every
  read, and `onLivingTick` called `SchoolData.getSchool(mob)` for **every** `Mob` in the world before its
  early-out. Every mob on the server was getting `ForgeData` forced into existence and written to disk.
- **B2/B3** `EntityJoinLevelEvent` fires for a villager whose profession is still `minecraft:none`;
  `pickVillagerSchool` returned null and `markNonCaster()` made that **sticky**, permanently barring every
  naturally-spawned villager from the feature under default config. Profession-scoped loadouts had the
  same hole.
- **B5** `LoadoutManager.resolve` wrote entity NBT and consumed `mob.getRandom()` — and was called from
  the documented read-only inspection command.
- **B7** `LineOfFire.isProtectedBystander` treated every `Player` as protected, so in multiplayer a
  hostile caster fighting player A silently never cast while player B stood near the firing line.
- **B12** `LineOfFire.clear` ran inside the per-spell loop with an unfiltered `getEntitiesOfClass`.

All of these are fixed in 0.6.0; see `CHANGELOG.md`.
